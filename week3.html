Week 3 · Day 1

PRD Sections 1–5 (Problem → Solution Sketch)

What You Do

Draft the first half of a Product Requirements Document: the problem/outcome statement, a solution sketch (user-visible flow, not implementation detail), and a first pass at acceptance criteria.

Why We Do This

The PRD is the first artifact engineering actually builds from, so this translates five weeks of discovery, metrics, and design work into a single build-ready document -- if any prior step was skipped, it becomes visible here as a section leadership can't fill in.

Key Artifacts

  • PRD draft (Sections 1-5)
  • Solution sketch

Connects To

This draft is deliberately incomplete -- it hands off directly to Day 2's acceptance-criteria hardening pass, because a solution sketch without testable AC is not yet buildable.

Week 3 · Day 2

Acceptance Criteria

What You Do

Write testable Acceptance Criteria that explicitly cover 'weird paths' (edge cases, error states, offline conditions) in addition to the happy path.

Why We Do This

An AC that only describes the happy path guarantees engineers will ask clarifying questions mid-sprint or ship a feature that breaks on the first edge case a real dispatcher hits. This is isolated as its own day because it is the single highest-leverage place a TPM prevents rework.

Key Artifacts

  • Acceptance Criteria set
  • Weird-path checklist

Connects To

The weird-path list drafted here is cross-checked against Day 3's NFR categories (what happens under bad network, high load, or invalid input) so reliability requirements aren't an afterthought.

Week 3 · Day 3

NFRs + Dependencies

What You Do

Define Non-Functional Requirements across 5 categories (Performance, Reliability, Security, Usability, Maintainability) in Requirement / Defense / Verification form, and log dependencies with a named owner and due-by date.

Why We Do This

An NFR that just says 'must be fast' can't be verified. Writing it as Requirement (the target), Defense (how the design meets it), Verification (how you'll prove it) forces the same rigor non-functional quality gets that functional features already have -- this is exactly how the course source material explains the Performance category.

Key Artifacts

  • NFR sheet (Requirement/Defense/Verification)
  • Dependency log with owners

Connects To

Named dependency owners and dates feed directly into Day 4's Risk section, since an unowned dependency is the most common hidden risk in a PRD.

Week 3 · Day 4

PRD Mini-Capstone (Risk + Draft Assembly)

What You Do

Assemble the full PRD draft -- problem statement through NFRs -- and add a Risks section with mitigations and explicitly flagged open decisions.

Why We Do This

This is the first day the PRD is judged as a whole artifact rather than section by section, which surfaces gaps that don't show up when sections are written in isolation (for example, an AC that contradicts an NFR). Naming open decisions explicitly, instead of quietly picking one, keeps leadership able to weigh in before build starts.

Key Artifacts

  • Assembled PRD draft
  • Risk register with mitigations
  • Open decisions list

Connects To

This assembled draft is the exact input to Day 5's peer review pass, where a second set of eyes scores it against the same rigor bar before it is called engineer-ready.

Week 3 · Day 5

PRD Review (Capstone)

What You Do

Run a structured peer review of the completed PRD against a scoring rubric, then revise it into a final, engineer-ready version.

Why We Do This

A PRD that only its author has read still carries that author's blind spots. Every PRD produced in the course is pressure-tested by a peer using the same rubric an engineering lead would use, closing the loop that started with Working Backwards in Week 1.

Key Artifacts

  • PRD review scorecard
  • Final engineer-ready PRD

Connects To

The revised, scored PRD is the exact document Week 4 Day 1 opens with -- architecture decisions are made against this PRD's constraints, not a rough draft.

How PRD Is Built and What Inputs It Needs

PRD is the bridge between strategy and build reality.

Required Inputs

  • Validated customer pain and personas
  • North Star + KPI hierarchy + baselines
  • User journey map and friction hotspots
  • Heuristic and accessibility findings
  • Business constraints and platform constraints
  • Technical dependencies and risk context

PRD Sections (TPM Quality)

  • Problem and outcome statement
  • Solution sketch (user-visible flow, not low-level code)
  • Acceptance criteria including weird paths
  • NFRs in Requirement / Defense / Verification form
  • Dependencies with owner and due-by date
  • Risks with mitigations and open decisions

Inputs → Draft → Cross-Review → Clarify Gaps → Engineer-Ready PRD
